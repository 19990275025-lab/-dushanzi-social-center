# 新媒体运营中心版本路线

> 版本前缀：`social-v`，与 OTA 的 `ota-v` 独立。
> 建议采用语义化版本号：`social-v主版本.次版本.修订号`。

## 1. 当前版本判断

- `package.json` 当前仍为 `0.1.0`。
- 仓库当前没有正式 Git tag。
- 代码功能已经明显超过初始化版本，但抖音连续数据稳定性、多平台真实数据和规则模型校准尚未达到正式 V1.0 标准。
- 因此建议把当前阶段定义为 **`social-v0.9.0` 候选基线**；本文档提交本身不创建 tag 或 Release。

## 2. 版本计划

### `social-v0.9.0`：快速开发集成阶段

现有基线：

- 新媒体运营驾驶舱及全局日期筛选。
- 抖音作品、评论、粉丝、观众数据的预览—确认—入库接口。
- WorkBuddy 热点接收、分析、推荐、复盘和档案。
- 内容监测、粉丝分析、评论洞察和规则型 AI 内容分析。
- AI 内容策划、任务看板、发布关联和效果复盘。
- Cloudflare D1、R2、Worker Cron 与 Sites 部署结构。

进入该版本 tag 前应完成：

- 构建、Lint、页面回归测试通过。
- 生产环境鉴权配置完成。
- 数据库和 R2 备份/回滚演练完成。
- 已知接口差异和未完成能力在文档中明确标注。

### `social-v1.0.0`：抖音完整闭环稳定版

必须达到：

- 热点监测：WorkBuddy 每日导入稳定，数量、平台、日期和重复处理可审计。
- 内容监测：至少连续 30 天抖音作品和评论数据稳定，作品详情指标口径与平台后台核对。
- 粉丝分析：总量、增长、流失、画像和活跃时间真实数据跑通，历史对比可用。
- AI 内容策划：A 级热点生成方案、生成任务、关联作品、7 日复盘完整验收。
- 任务管理：八阶段拖拽、逾期、负责人统计和自动作品关联稳定。
- 数据采集：所有正式写入均经过预览和人工确认，失败日志和恢复步骤可执行。
- 安全：外部接口鉴权、敏感信息管理、上传限制和最小权限完成生产检查。

V1.0 不要求：快手/微博内容自动采集、视频号、复杂 OCR 或大模型自动运营。

### `social-v1.1.0`：AI 分析与日报周报优化

目标：

- 为规则模型增加版本号、人工复核样本和准确率指标。
- 优化热点、内容、粉丝、评论的日报/周报口径与导出质量。
- 增加数据新鲜度、完整率、异常值和采集失败监控。
- 在明确安全、成本和人工审核机制后，评估接入大模型 API；生成内容必须可追溯并可人工编辑。
- 统一旧版/兼容采集接口的生命周期说明。

### `social-v2.0.0`：快手与微博

目标：

- 接入合规、稳定的快手作品/评论/粉丝数据源。
- 接入微博内容、互动、粉丝和品牌传播数据源。
- 校准各平台指标，禁止将不同平台的热度或互动口径直接等同。
- 内容监测、粉丝分析、策划和任务形成平台差异化策略。
- MediaCrawler 如通过合规与技术评估，以独立适配器调用统一 V2 API，不把采集依赖嵌入主站。

### `social-v3.0.0`：视频号及全平台统一运营

远期目标：

- 在重新评估产品需求、平台授权和数据库枚举后接入视频号。
- 形成跨平台账号、内容、粉丝、热点、任务与复盘的统一运营视图。
- 建立跨平台去重、内容复用、渠道归因和权限治理。

注意：视频号已从当前系统范围移除，V3.0 只是远期路线，不代表现有 schema/API 已兼容。启动前必须形成独立架构与迁移方案。

## 3. 发布规则

### 3.1 分支和提交

- 主分支：`main`。
- 功能分支建议：`codex/<short-description>` 或团队约定前缀。
- 提交必须带模块范围，例如：

```text
feat(social): 新增粉丝画像历史对比
fix(social): 修复热点日期筛选
docs(social): 更新数据采集接口说明
```

- OTA 仓库使用 `feat(ota)` 等独立范围，不在本仓库混入 OTA 代码。

### 3.2 Tag 和 Release

```bash
git tag -a social-v1.0.0 -m "抖音完整闭环稳定版"
git push origin social-v1.0.0
```

创建 tag 前必须：

1. 更新 `CHANGELOG.md`。
2. 确认 `main` 与 `origin/main` 同步且工作区干净。
3. 执行 Lint、构建和关键流程测试。
4. 记录数据库迁移、部署地址、回滚提交和负责人。
5. 禁止复用或强制移动已经发布的 tag。

## 4. 版本验收矩阵

| 能力 | v0.9 | v1.0 | v1.1 | v2.0 | v3.0 |
|---|---:|---:|---:|---:|---:|
| 抖音采集与监测 | 集成 | 稳定 | 优化 | 保持 | 保持 |
| WorkBuddy 热点闭环 | 集成 | 稳定 | 模型优化 | 多平台校准 | 全平台 |
| 内容/粉丝/评论分析 | 规则版 | 稳定版 | 精度与报告优化 | 快手/微博 | 视频号 |
| AI 内容策划与任务 | 基础闭环 | 稳定闭环 | 智能增强 | 多平台 | 统一编排 |
| MediaCrawler / Agent-Reach | 评估 | 非必需 | 可选验证 | 视合规接入 | 统一治理 |
| 正式 Git tag | 无 | 必须 | 必须 | 必须 | 必须 |

## 5. 不兼容变更原则

- 删除字段、改变平台枚举、重定义指标或改动确认流程属于不兼容变更，应提升主版本或提供迁移期。
- 数据库迁移必须可回滚，并在 CHANGELOG 的“数据库调整”中单独列出。
- API 字段只新增通常可进入次版本；删除/改名必须提供版本化端点。
- 任何采集来源变更都要记录来源、时间、授权、字段完整率和数据口径。
